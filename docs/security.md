# Модель безопасности Beta 0.2

## Неприкосновенность существующих данных

Менеджер не форматирует диски, не меняет разделы и не переносит существующие пользовательские файлы. Core записывает только в собственный каталог с маркером `.cloud-storage-root.json` и отказывается занимать непустой немаркированный каталог. Удаление из API является мягким: объект переносится в `.trash`, а метаданные и аудит сохраняются.

## Загруженные файлы — данные, а не программы

- сервер никогда не запускает загруженный путь и не передаёт его shell-интерпретатору;
- содержимое хранится вне каталогов приложения, службы и автозапуска;
- клиентское имя проходит нормализацию, а физическое имя является случайным идентификатором с расширением `.blob`;
- `..`, абсолютные пути, управляющие символы и опасные варианты логического пути отвергаются;
- загрузка атомарно фиксируется только после проверки размера, SHA-256, квоты и доступного места;
- Unix-биты исполнения удаляются, управляемый объект переводится в режим только чтения;
- API выдаёт объект как вложение, запрещает MIME-sniffing и не распаковывает архивы;
- временная загрузка удаляется при ошибке или отмене.

Флаг read-only сам по себе не является полной защитой Windows от запуска. Основные барьеры здесь — отсутствие любых путей исполнения в Core, непрозрачное размещение и изоляция каталога. Усиленные системные WDAC/AppLocker-политики может отдельно включить администратор; приложение не меняет глобальную политику ОС самовольно.

## Секреты и учётные данные

Пароли хранятся только как Argon2id-хеш. Коды приглашений и токены устройств сохраняются как HMAC-отпечатки; открытый токен возвращается клиенту один раз. Секрет менеджера и HMAC-ключ создаются криптографическим генератором в `core-secrets.json`, исключены из обычных настроек и аудита и получают ограниченный ACL/режим файла.

Административные маршруты используют отдельный bearer-токен менеджера. Запросы устройств используют индивидуальные отзываемые токены. Код приглашения одноразовый, ограничен по времени, защищён лимитом попыток и всё равно требует последующего подтверждения устройства администратором.

## Сетевая граница

Административный API принимает только `127.0.0.1`, `::1` или `localhost`. Опциональный LAN-вход использует отдельный HTTPS-порт и постоянную локальную пару RSA-ключ/сертификат. На нём middleware скрывает `/v1/admin`, `/docs`, `/redoc` и `/openapi.json`. Приватный ключ получает ограниченные права и никогда не включается в приглашение; наружу передаётся только SHA-256-отпечаток публичного сертификата.

Удалённый вход включается отдельно и использует третий HTTPS-порт. Его граница работает по принципу default deny: разрешены только точные маршруты здоровья, подключения устройства, пространств, файлов и возобновляемых загрузок; любой административный, служебный или будущий неизвестный маршрут возвращает `404`. Даже корректный секрет Manager не открывает административный API через этот listener. Удалённое погашение одноразовых кодов имеет отдельный выключатель и по умолчанию запрещено; для него действует более строгий лимит попыток. Общий внешний трафик ограничен по адресу, а разрешённые и отклонённые обращения записываются в серверный аудит без токенов и содержимого файлов.

Core не использует UPnP, не перенастраивает роутер и не меняет firewall. Администратор явно подтверждает включение и самостоятельно выбирает VPN либо ручное перенаправление одного TCP-порта. Указанный публичный адрес обязан быть HTTPS-origin без учётных данных, query, fragment или дополнительного пути. Client запрещает незашифрованный удалённый HTTP и закрепляет SHA-256-отпечаток сертификата; для каждого сохранённого сервера применяется отдельный токен.

Desktop Client Alpha 0.3 запрещает обычный HTTP для любых адресов, кроме loopback. Для HTTPS он проверяет системно доверенный сертификат либо точный SHA-256-отпечаток на реальном соединении. UDP-обнаружение само по себе не является доказательством личности сервера, поэтому пользователь должен сверить отпечаток; полное приглашение доставляет его вместе с кодом. Токен устройства не записывается в обычный JSON-профиль: Windows-версия защищает его DPAPI, Linux-версия использует отдельный файл с правами `0600` до интеграции с Secret Service.

Незавершённые загрузки пишутся только в управляемый `.staging`, привязаны к пользователю и имеют срок действия. Core проверяет точное смещение каждого блока, итоговый размер и необязательный ожидаемый SHA-256 до атомарной фиксации. Клиент сохраняет частично скачанный файл с суффиксом `.part` и заменяет конечный путь только после полной проверки SHA-256.

Перенос между дисками касается только объектов внутри управляемых корней. Источник должен быть переведён в режим без новых записей. Копия сначала полностью записывается в staging целевого корня, синхронизируется и проверяется по сохранённым размеру и SHA-256; метаданные переключаются условной транзакцией. Исходный объект в Alpha 0.4.0a2 не удаляется автоматически.

Зеркальная реплика создаётся только в отдельном управляемом корне с ролью `mirror`. Она публикуется после проверки размера и SHA-256, не подменяет основную запись в метаданных и не используется для новых загрузок как дополнительная ёмкость. При недоступности основного объекта чтение переключается лишь на реплику с точным совпадением идентификатора файла, версии, размера и SHA-256; повреждённая или устаревшая реплика исключается заданием сверки.

Диагностика работает только на чтение относительно пользовательских объектов. Она проверяет границы управляемых путей, запрещает доверять символьным ссылкам и в полном режиме сравнивает фактический SHA-256 с метаданными. Обнаружение проблемы создаёт инцидент и рекомендацию, но не удаляет, не перезаписывает и не «чинит» основной файл автоматически. Запуск полной проверки и просмотр деталей доступны только через локальный административный API.

Резервный снимок пишется только на корень с явной ролью `backup`, который исключён из обычного распределения загрузок. Снимок не становится готовым, пока не созданы согласованная копия базы, манифест и все объекты с совпадающими размером и SHA-256. Частичный staging-каталог удаляется при отмене или ошибке.

Проверяемое восстановление не выполняет полный откат базы и не доверяет одному имени файла из снимка. Оно использует только завершённый снимок внутри управляемого backup-корня, проверяет containment, размер и SHA-256, а затем условно заменяет ссылку лишь если живые метаданные всё ещё совпадают с версией снимка. Исправные объекты и более новые версии пропускаются. Поэтому операция устраняет потерю физического объекта, но не отменяет последующие изменения пользователя.

Аварийный режим `read_only` включается только локально авторизованным Manager с явным подтверждением и записывает причину в аудит. Он является оперативным барьером от новых изменений, а не заменой резервных копий или системных ACL. Диагностика и скачивание продолжают работать; отзыв скомпрометированного устройства специально остаётся доступным. Возврат в обычный режим также журналируется.

Автоматическая политика не считает снимок пригодным только потому, что его каталог существует. Перед ротацией Core проверяет SQLite снимка и выполняет полный пробный цикл чтения/записи каждого объекта на выбранном основном корне. Неуспешная проверка сохраняется как ошибка и запрещает удалять эту копию политикой. Активно используемый восстановлением снимок также исключается из очистки.

Удаление по политике ограничено одним непосредственным дочерним каталогом управляемого `backups`; символьные ссылки и выход за границу корня отвергаются. Переименование в `.staging` предшествует транзакции метаданных, поэтому сбой базы не оставляет запись о несуществующем снимке. Каждое удаление получает отдельное событие аудита.
