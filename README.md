# Cloud Storage Server

Домашний облачный сервер для Windows, Linux, macOS, Android и iOS. Версия **0.9.19** завершает живые статусы пользователей и управление физическими дисками.

Текущая ветка также содержит полный слой **Idea 4**: системные профили, питание/ИБП,
Telegram/email/webhook, 20 шаблонов автоматизаций, отчёты, безопасные контейнерные
ячейки, файл входа нового пользователя, простой интерфейс и Apple-сборки для
MacBook/iPhone/iPad. Подробности: [docs/idea4.md](docs/idea4.md).

## Что работает в версии 0.9.14

- обычный вход Client использует только логин и пароль, а первый вход через интернет — одноразовую ссылку, файл или QR без пароля;
- ссылка и QR содержат основной и резервные адреса сервера и не показывают пользователю IP, URL или TLS-отпечаток;
- Server Manager защищённо сохраняет созданные и сброшенные пароли средствами учётной записи Windows, чтобы администратор мог показать и скопировать пароль;
- постоянные Server/Client Installer сами получают подписанный каталог и позволяют установить последнюю либо выбранную старую версию;
- `.cloud-access.json` не содержит постоянного пароля, действует до 7 дней, используется один раз и создаёт ожидающее подтверждения устройство;
- пользователи имеют email, редактируемую роль, квоту, состояние и подробные права; пароль хранится только как Argon2id-хеш;
- SMTP отправляет файл входа настоящим вложением;
- общие логические пространства получают основной и резервный физический диск, отдельные права и отдельные буквы в Проводнике;
- при недоступности основного диска новые объекты пишутся на резервный, а ручной перенос обратно проверяет размер и SHA-256 и пишется в аудит;
- обновления различают сетевые ошибки, 404, повреждение и неверную подпись, а установщик проверяется по подписи каталога, размеру и SHA-256.

## Что изменено в версии 0.9.19 — пользователи и диски

- динамический код подключения расположен над сворачиваемым списком пользователей;
- для пользователя видны дата создания, последний вход и цветное живое состояние от офлайна до передачи или удаления;
- удаление учётных записей заблокировано в интерфейсе и административном API, доступно безопасное отключение;
- физические диски показывают подтверждённые Windows объёмы, модель, серийный номер, интерфейс, нагрузку и скорости ввода-вывода;
- системный диск защищён от использования хранилищем, а виртуальные тома Client и Google Drive исключены из физических дисков;
- подробные права можно массово применить ко всем общим пространствам выбранного диска;
- меню диска запускает Проводник, проверку ошибок, штатную оптимизацию, безопасное удаление из Manager и форматирование с двойным подтверждением;
- недоступный каталог диска возвращает понятную ошибку настройки вместо HTTP 500.

## Что изменено в версии 0.9.18 — переход на zrok2

- удалённый tunnel-provider по умолчанию запускает актуальный бинарник `zrok2`;
- обычный интернет-доступ использует `zrok2 share public --headless`;
- постоянное публичное имя подключается через `-n public:<имя>` вместо удалённой из zrok2 команды `share reserved`;
- старое стандартное значение `zrok` в настройках автоматически заменяется на `zrok2`, а явно указанный полный путь к zrok v1 остаётся совместимым;
- Core передаёт процессу разрешённые переменные `ZROK2_*`, но по-прежнему не передаёт пароли и токены Cloud Storage.

## Native Go Core

- `CloudStorageServerCore.exe` и `CloudStorageServerService.exe` собраны на Go и работают без Python-консоли;
- системный mutex гарантирует один экземпляр Core без накопления процессов;
- Go-watchdog запускает внутренний compatibility engine, контролирует его и восстанавливает после сбоя;
- старый `core.pid` проверяется по реальному имени процесса и больше не блокирует запуск из-за PID `svchost.exe`;
- Uvicorn не использует несовместимый с Windows Service консольный formatter;
- холодный запуск получает до 30 секунд, а локализованный вывод `sc.exe` декодируется через OEM-кодировку Windows;
- установщик обновляет службу, удаляет устаревшую PID-блокировку и сохраняет базу, пользователей и настройки;
- публичный API `v1` не изменён, поэтому Manager, Desktop Client и мобильные приложения совместимы без перенастройки;

- все системные вкладки открываются без запущенного Core и подсвечиваются при наведении;
- в Настройках есть прямые разделы Система, Интерфейс, Docker и SSH;
- кнопка сохранения показывается только после реального изменения;
- диагностика запуска Core объясняет причину и показывает путь к журналу;
- Docker, SSH и лимиты контейнера имеют безопасную автонастройку;
- периодический health-check вынесен из UI-потока, поэтому открытые вкладки не подвисают;
- post-install запуск Manager использует UAC-совместимый ShellExecute, а runtime-иконки берутся из общего ресурса;

- повторный запуск Manager или Desktop Client активирует существующее окно и не создаёт новый процесс;
- Core/Service, виртуальный диск, установщики и мобильный фоновый worker защищены от параллельных копий;
- вкладка «Docker и SSH» устанавливает Docker Desktop, показывает готовность движка и настраивает Windows OpenSSH Server;
- SSH разрешает одного локального администратора, работает только по публичному ключу и открывает порт только для частной сети;
- контейнеры скриптов и ботов имеют явный переключатель сети, read-only основу и лимиты CPU/RAM/диска;
- вкладка «Система» объединяет профили, интерфейс, безопасность, питание, zrok, Telegram, email, webhook, отчёты, автоматизации и контейнерные ячейки;
- 10 аварийных и 10 обычных готовых автоматизаций, включая безопасное выключение через час при потере питания и восстановление зеркала;
- простой режим оставляет основные разделы и центральное меню «Разделы», подробный режим показывает всю навигацию;
- создание пользователя сразу готовит личный диск, одноразовый код, файл входа, ссылку скачивания и отправку через настроенный SMTP;
- Windows-клиент ставит WinFsp и создаёт личные виртуальные диски в Проводнике; zrok публикует только клиентский HTTPS-вход;
- мобильные Client/Manager имеют раздельные Android и iPhone/iPad сборки, MacBook получает отдельные Manager/Client DMG через CI.

- пробное восстановление открывает копию SQLite и последовательно копирует каждый объект снимка во временную область основного диска с проверкой размера и SHA-256, не меняя рабочие метаданные;
- политика хранения удаляет только успешно проверенные старые снимки, никогда не трогает активное восстановление и оставляет заданное число последних копий;
- ротация сначала атомарно перемещает снимок в управляемый карантин, затем фиксирует аудит и только после этого удаляет файлы.
- отдельный удалённый HTTPS-вход разрешает только клиентские маршруты и возвращает `404` для административного API, документации и неизвестных будущих путей;
- внешний доступ и удалённое подключение по коду включаются раздельно и только после явного подтверждения администратора;
- действуют отдельные лимиты запросов и попыток подключения, а Manager показывает журнал разрешённых и отклонённых внешних обращений;
- программа не использует UPnP и не меняет роутер/firewall: рекомендуется VPN, прямое перенаправление одного порта настраивается вручную;
- Desktop Client хранит несколько независимых серверных профилей с отдельными TLS-отпечатками и защищёнными токенами;
- старый одиночный профиль и токен автоматически мигрируют при первом запуске версии 0.5.0.

Удалённый доступ по умолчанию выключен. Для включения откройте в Server Manager расширенный режим → «Удалённый доступ», укажите публичный HTTPS-origin и подтвердите запуск отдельного порта. Для выдачи нового приглашения временно включите отдельный флаг подключения по коду; уже подтверждённым устройствам он не нужен.

## Что уже работает в версии 0.6.0 — этап 6 завершён

- центр уведомлений хранится в SQLite, поддерживает подтверждение сообщений и доставку через Manager Inbox и системный журнал Core;

- для инцидента можно безопасно запустить повторную проверку, очистить только просроченные временные загрузки или после подтверждения защитить сервер режимом только чтения;
- Manager полностью управляет правилами, уведомлениями, интеграциями и действиями диагностики; все изменения записываются в аудит и переживают перезапуск Core.

## Как работает подключение человека

1. Администратор запускает ядро в Server Manager и создаёт пользователя с квотой, логином и временным паролем.
2. Человек вводит адрес сервера, логин, пароль и название устройства в Desktop Client либо мобильном приложении.
3. Устройство появляется у администратора со статусом «Ожидает» и пока не видит файлы.
4. После ручного подтверждения устройство получает доступ только к пространствам этого пользователя.
5. На другом компьютере или телефоне человек использует тот же логин и пароль, но новое устройство снова требует отдельного подтверждения.

Одноразовый код и QR продолжают работать как резервный способ первого подключения. Код действует 15 минут, используется один раз и не отменяет ручное подтверждение устройства.

## Подключение второго компьютера в локальной сети

1. В Server Manager переключитесь в расширенный режим и откройте «Настройки → Сеть».
2. Включите защищённое LAN-подключение и сохраните настройки: Core безопасно перезапустится.
3. В Windows разрешите входящие подключения только для частных сетей, если появится системный запрос.
4. Откройте Client на втором компьютере, нажмите «Найти в сети» и войдите тем же логином и паролем. Одноразовое приглашение остаётся резервным вариантом.
5. При поиске вручную сверьте начало SHA-256-отпечатка с Server Manager перед вводом пароля. Полное приглашение уже содержит закреплённый отпечаток.

## Подключение из интернета

1. Установите актуальный zrok2 по официальной инструкции, получите токен аккаунта и один раз выполните `zrok2 enable <токен>` от имени учётной записи, под которой работает Core.
2. В Server Manager откройте расширенный режим → «Удалённый доступ», включите zrok2 и сохраните настройки. После запуска Manager покажет публичный HTTPS-адрес. Роутер и firewall менять не нужно.
3. В Desktop Client или Mobile введите публичный HTTPS-адрес, логин, пароль и название нового устройства. Подключение по одноразовому коду можно временно разрешить только как резервный способ.
4. Подтвердите новое устройство в Manager, затем в клиенте выполните защищённый интернет-вход тем же логином и паролем.
5. Альтернативы остаются прежними: VPN либо отдельный прямой HTTPS-порт с ручной настройкой. Все внешние файловые запросы требуют интернет-сессию.

## Быстрый запуск из исходников

Нужен Python 3.11 или новее.

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -e ".[dev,build]"
.\.venv\Scripts\python -m cloud_storage
```

### Linux

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev,build]'
.venv/bin/python -m cloud_storage
```

Ядро можно запустить отдельно:

```powershell
.\.venv\Scripts\python -m cloud_storage.core
```

Desktop Client запускается отдельно:

```powershell
.\.venv\Scripts\python -m cloud_storage.client
```

Интерактивная схема локального API после запуска доступна по адресу `http://127.0.0.1:8765/docs`. Административные маршруты требуют секрет менеджера и предназначены для Server Manager.

## Проверка и сборка

```powershell
.\.venv\Scripts\python -m pytest
.\.venv\Scripts\python -m ruff check .
.\scripts\build-installers.cmd
```

В Linux используйте `./scripts/build.sh`. Результаты находятся в:

- `dist/CloudStorageServerManager`;
- `dist/CloudStorageServerCore`;
- `dist/CloudStorageServerService` на Windows.
- `dist/CloudStorageClient`.
- `dist/CloudStorageDrive.exe` на Windows;
- два постоянных онлайн-установщика и два внутренних пакетных установщика версий в `outputs`.

Автономная сборка не требует установленного Python на компьютере пользователя.

Оба Windows-установщика собираются одной командой
`powershell -ExecutionPolicy Bypass -File scripts/build-installers.ps1`. Для сборки нужны
Go 1.25+ и Inno Setup 6. Скрипт скачивает ровно WinFsp 2.1.25156 и принимает его только при
совпадении закреплённого SHA-256. Python, Go и Inno Setup на компьютере пользователя не нужны.

Пользователь сохраняет `CloudStorage-Client-Installer-windows-x64.exe` или
`CloudStorage-Server-Installer-windows-x64.exe` один раз. Постоянный установщик получает
подписанный каталог, предлагает последнюю стабильную либо конкретную старую версию, затем
проверяет размер и SHA-256 пакетного установщика. При обновлении серверная SQLite-база и
настройки сохраняются, а перед миграцией создаётся резервная копия.

Манифесты публикации создаются `scripts/sign-update-manifest.py`. Закрытый Ed25519-ключ нельзя
добавлять в репозиторий или выпуск; приложение содержит только публичный ключ проверки.

## Фоновая служба

Windows (PowerShell от имени администратора):

```powershell
.\scripts\install-service.ps1
```

Linux (пользовательская systemd-служба):

```bash
./scripts/install-service.sh
```

Удаляющие службу сценарии сохраняют базу и файлы сервера. Windows-данные по умолчанию находятся в `%PROGRAMDATA%\CloudStorage`, Linux-данные — в `~/.local/share/cloud-storage`. Путь ядра можно переопределить через `CLOUD_STORAGE_CORE_DATA_DIR`.

Настройки интерфейса хранятся отдельно: `%LOCALAPPDATA%\CloudStorage\settings.json` в Windows или `${XDG_CONFIG_HOME:-~/.config}/cloud-storage/settings.json` в Linux.

Настройки Desktop Client и зашифрованный токен находятся в `%LOCALAPPDATA%\CloudStorageClient` в Windows или `${XDG_CONFIG_HOME:-~/.config}/cloud-storage-client` в Linux.

База вкладки «Помощь» хранится локально в `knowledge.db` рядом с настройками соответствующего приложения. Этот помощник не является облачной нейросетью и не передаёт вопросы, токены или файлы в интернет. В дальнейшем поверх той же базы можно подключить необязательную генеративную модель с явным согласием администратора.
