# Cloud Storage — полное описание продукта

> Актуально для **Cloud Storage 0.10.8 beta 2**. Это честное техническое описание текущего состояния продукта, пригодное как основа для сайта. Функции, которые ещё находятся в разработке или требуют дополнительной проверки, отмечены отдельно.

## Коротко

**Cloud Storage — это самостоятельное домашнее или небольшое корпоративное облако, которое работает на вашем компьютере и ваших дисках.** Сервер хранит файлы, управляет пользователями, правами и резервными копиями, а клиент даёт доступ к данным через приложение, браузер и виртуальные диски в Проводнике Windows.

В отличие от обычных облачных сервисов, основное хранилище находится не у разработчика и не на обязательном стороннем сервере. Владелец сам выбирает компьютер, физические диски, пользователей и способ доступа из интернета.

## Что это за продукт

Cloud Storage состоит из нескольких связанных компонентов:

- **Server Manager** — графическое приложение администратора. Через него настраиваются диски, логические пространства, пользователи, подключения, резервные копии, обновления, диагностика и автоматизации.
- **Server Core** — серверное ядро, которое отвечает за API, базу данных, права, загрузку и скачивание файлов, контроль целостности, pairing устройств и фоновые операции.
- **Desktop Client** — приложение пользователя для Windows. Оно подключается к серверу, показывает файлы и передачи, поддерживает локальный кэш и управляет виртуальными дисками.
- **CloudStorageDrive** — отдельный компонент виртуального диска на Go. С помощью WinFsp он показывает разрешённые пространства как обычные диски в Проводнике Windows.
- **Веб-клиент** — встроенная страница сервера для доступа через браузер без установки Desktop Client.
- **Мобильные приложения** — отдельные Client и Manager для Android/iOS. Сейчас они относятся к более ранней линии 0.9.14 и не равны по готовности Desktop Client 0.10.8 beta.
- **Постоянные установщики** — установщики сервера и клиента, способные получать доступные версии из подписанного каталога обновлений.

Основной и наиболее полно проверяемый сценарий сейчас — **сервер и клиент на Windows**.

## Для кого подходит Cloud Storage

Cloud Storage предназначен для людей и небольших команд, которым нужно:

- хранить данные на собственных HDD или SSD;
- открывать домашние файлы с другого компьютера;
- дать членам семьи или сотрудникам раздельный доступ;
- использовать несколько логических пространств, например «Личное», «Семья», «Фото» и «Команда»;
- видеть хранилище как обычный диск в Проводнике;
- работать через браузер;
- самостоятельно контролировать резервные копии, права и внешний доступ;
- не зависеть от фиксированного тарифа облачного провайдера за каждый гигабайт.

Это не замена дата-центру с гарантированным SLA и не готовое сертифицированное решение для банковских, медицинских или государственных секретов.

## Как всё работает

### 1. Установка и запуск сервера

Администратор устанавливает Server Manager и Server Core на компьютер, который будет сервером. Core запускается как отдельный процесс или системная служба. Manager остаётся интерфейсом управления и не хранит файлы самостоятельно.

Административный API по умолчанию слушает только `127.0.0.1`, то есть доступен на самом сервере. Пользовательский доступ включается отдельно для локальной сети или через защищённый интернет-канал.

### 2. Подключение физических дисков

В Manager выбираются физические диски и каталоги. Им можно назначить роли:

- основное хранилище;
- резервный корень для новых записей при отказе основного;
- staging или кэш приёма;
- зеркало;
- архив;
- место для резервных снимков.

Для каждого корня можно задать приоритет, минимальный остаток свободного места и предел заполнения. Системный диск и неподходящие виртуальные тома должны отсеиваться защитными проверками.

### 3. Создание логических пространств

Пользователь работает не с физическими путями сервера, а с логическими пространствами. Например, папки на одном большом HDD могут быть представлены как отдельные диски «Фото», «Документы» и «Семья».

У пространства есть:

- уникальный идентификатор;
- название и квота;
- основной и резервный storage root;
- список участников;
- подробные права на просмотр, загрузку, изменение, удаление и создание общих ссылок.

Физический путь сервера пользователю не раскрывается.

### 4. Первичное подключение устройства

Server Manager показывает динамический код формата `CS3.…`. Внутри защищённого контейнера находятся идентификатор сервера, доступные адреса, параметры проверки TLS, срок действия и nonce.

Код:

- обновляется каждые пять минут;
- проверяется сервером;
- защищён HMAC-SHA-256 от незаметного изменения;
- используется для первоначального pairing;
- ограничивается по частоте попыток.

Пользователь вставляет код в Desktop Client или на веб-странице. Клиент извлекает адреса, пробует доступные варианты подключения и отправляет код серверу. После успешной проверки сервер создаёт или привязывает учётную запись и доверенное устройство.

Код не является постоянным паролем. После первого подключения устройство получает отдельные учётные данные и может автоматически восстанавливать соединение, пока администратор не отзовёт доступ.

### 5. Работа с файлами

Когда пользователь загружает файл, Core сначала пишет его во временный управляемый каталог `.staging`. Во время приёма сервер контролирует смещение блоков, размер и, когда доступно, ожидаемый SHA-256. Только после успешной проверки объект атомарно публикуется в основном хранилище, а метаданные записываются в SQLite.

Физические имена объектов случайны и не повторяют пользовательский путь. Соответствие между логическим именем, версией и физическим объектом хранится в базе данных.

Удаление не обязано сразу уничтожать данные: объект может быть перемещён в управляемую корзину. Для файлов поддерживаются версии, контроль целостности и проверяемые операции переноса между дисками.

### 6. Виртуальный диск в Windows

Desktop Client запускает отдельный процесс CloudStorageDrive для разрешённого пространства. WinFsp создаёт диск с выбранной буквой в Проводнике.

Содержимое каталога загружается по требованию. При открытии файл скачивается в локальный staging-кэш, а изменения отправляются на сервер при синхронизации или закрытии файла. Кэш по умолчанию ограничен 10 ГБ и может быть настроен в диапазоне 10–30 ГБ для каждого сервера. Это максимальный объём кэша, а не заранее занятый фиктивный файл.

Токен устройства не передаётся в командной строке и не хранится открытым текстом в обычном профиле. В Windows он защищается средствами DPAPI текущей учётной записи.

### 7. Доступ через браузер

Встроенный веб-клиент использует тот же Core и те же серверные права. Через него можно пройти первичное подключение по актуальному коду, войти в существующую учётную запись, просматривать пространства, создавать папки, загружать, скачивать, переименовывать и удалять файлы в пределах выданных разрешений.

Опция «доверенное устройство» сохраняет длительную сессию. Без неё веб-сеанс ограничен и после выхода или истечения срока потребуется новый вход.

### 8. Доступ через интернет

Cloud Storage не открывает домашний роутер автоматически через UPnP. Владелец осознанно выбирает один из вариантов:

- VPN между устройствами;
- собственный HTTPS-домен и перенаправление одного TCP-порта;
- Cloudflare Tunnel;
- zrok2.

Cloudflare Tunnel и zrok2 подключаются только к выделенному пользовательскому веб/API backend на loopback-интерфейсе. Локальный административный API Manager через них не публикуется.

Публичный URL должен использовать HTTPS. Для прямого HTTPS-подключения Client проверяет системно доверенный сертификат или закреплённый SHA-256-отпечаток сертификата.

## Какие протоколы и технологии используются

### Основной файловый протокол

Cloud Storage использует собственный версионированный API `/v1` поверх **HTTP/HTTPS**:

- JSON — для учётных записей, пространств, папок, прав, заданий и метаданных;
- бинарное тело HTTP — для содержимого файлов;
- блочные и возобновляемые операции — для продолжения передачи после обрыва;
- HTTP Range — для докачки скачивания;
- TLS — для защищённого доступа по сети.

Это не SMB, не FTP, не SFTP и не WebDAV. Проводник работает через локальный WinFsp-мост, а сам мост общается с сервером через API Cloud Storage.

### Дополнительные протоколы и интеграции

- **UDP discovery** — поиск сервера в локальной сети. Обнаружение помогает найти адрес, но само по себе не подтверждает личность сервера.
- **HTTPS + cookie/CSRF** — веб-интерфейс и браузерные сессии.
- **Cloudflare Tunnel или zrok2** — опциональная публикация пользовательского HTTPS-входа в интернет.
- **SMTP с TLS/STARTTLS и Gmail OAuth** — отправка приглашений и уведомлений по email.
- **Telegram Bot API по HTTPS** — уведомления администратора.
- **HTTPS webhooks** — интеграция с внешними системами.
- **SSH по публичному ключу** — отдельная административная функция для частной сети; она не является файловым протоколом Cloud Storage.
- **Docker/Podman** — изолированные контейнерные ячейки для разрешённых задач и ботов; это дополнительная серверная функция.
- **SQLite в режиме WAL** — локальная база метаданных, пользователей, устройств, прав, заданий и аудита.
- **Ed25519** — подпись каталогов обновлений.
- **Argon2id** — хеширование пользовательских паролей.
- **SHA-256** — проверка целостности файлов, пакетов обновлений и операций копирования.

## Безопасность

### Разделение административного и пользовательского доступа

Manager API доступен только на loopback-интерфейсе сервера. Внешние listener-ы используют точный список разрешённых маршрутов: неизвестные и административные пути не должны публиковаться наружу.

### Учётные записи и устройства

Пароль хранится на сервере как Argon2id-хеш, а не в исходном виде. После pairing каждое устройство получает собственный токен. Администратор может отключить пользователя или отозвать конкретное устройство.

Секреты кодов и токенов в базе представлены хешами или проверяемыми отпечатками. Исходный токен выдаётся клиенту только в момент создания.

### Защита сетевого соединения

Удалённый доступ допускается только по HTTPS. Клиент использует системную цепочку доверия сертификату или certificate pinning. Обычный HTTP разрешён только для loopback-сценариев на том же компьютере.

### Права на файлы

Права проверяются на стороне Core для каждого действия, а не только скрывают кнопки в интерфейсе. Для пространства отдельно задаются просмотр и скачивание, загрузка и создание папок, изменение, перемещение, переименование, удаление и создание общих ссылок.

### Целостность данных

Загрузка фиксируется только после проверки размера и SHA-256. Переносы, зеркала, резервные снимки и восстановление используют staging, проверку границ управляемого каталога, размер и SHA-256. Полная диагностика может пересчитать хеши, но не исправляет пользовательские объекты самовольно.

### Обновления

Каталоги версий подписываются Ed25519. До запуска установщика проверяются подпись каталога, имя пакета, размер и SHA-256. Переход редиректа с HTTPS на незащищённый HTTP должен блокироваться.

### Локальные секреты

В Windows токены Desktop Client защищаются DPAPI. Мобильные приложения используют Keychain/Keystore. Туннельный процесс не должен получать пароль пользователя, токен устройства или секрет Manager.

### Аудит и аварийный режим

Значимые административные и файловые действия записываются в аудит. При инциденте администратор может включить режим только для чтения: скачивание и диагностика сохраняются, а новые изменения блокируются до ручного отключения режима.

## Общие ссылки

Desktop Client и веб-клиент могут создать публичную ссылку на отдельный файл. Ссылка содержит криптографически случайный bearer-token, действует ограниченное время — в текущей beta по умолчанию семь дней — и может быть отозвана владельцем.

Изображения, видео, аудио и текст можно открыть на отдельной странице предварительного просмотра. Остальные форматы скачиваются. Страница не должна раскрывать список других файлов пространства.

Важно: любой, кто получил действующую ссылку, может открыть выбранный файл. Такую ссылку следует считать секретом и передавать только через доверенный канал.

## Резервирование и восстановление

Cloud Storage поддерживает несколько разных механизмов:

- резервный storage root для новых записей, если основной недоступен или достиг порога заполнения;
- зеркальную копию объектов на отдельном корне;
- резервные снимки базы и объектов;
- проверяемое восстановление потерянных физических объектов;
- ручной возврат данных с резервного диска на основной после его восстановления.

Копия не считается готовой только потому, что каталог создан. Core проверяет согласованность базы, наличие объектов, размер и SHA-256. Тем не менее одна серверная машина не заменяет полноценную схему резервного копирования. Как минимум одна копия важных данных должна находиться на другом физическом устройстве, а для действительно ценных данных — ещё и вне помещения.

## Автоматизации и управление

Server Manager содержит диагностику, отчёты, уведомления, контроль питания и ИБП, политики резервного копирования, автоматизации, Docker/Podman и SSH. Опасные действия должны требовать явного подтверждения и записываться в аудит.

Автоматизации работают через фиксированный список поддерживаемых действий. Они не предназначены для бесконтрольного выполнения произвольной команды оболочки, скрипта или URL из правила.

## Можно ли доверять Cloud Storage

### Короткий ответ

**Для домашнего тестирования, личной лаборатории и некритичных данных — да, при правильной настройке и наличии независимой резервной копии. Для единственной копии незаменимых данных или высокосекретной информации — пока нет.**

### Что даёт основания для доверия

- данные хранятся на выбранном владельцем оборудовании;
- административный API отделён от пользовательского;
- удалённый доступ требует HTTPS;
- пароли хешируются Argon2id;
- устройства имеют отдельные отзываемые токены;
- загрузки, переносы и обновления проверяются криптографическими хешами;
- обновления используют цифровую подпись Ed25519;
- права проверяются сервером;
- есть аудит, диагностика, корзина, версии, резервные снимки и режим только для чтения;
- исходный код доступен для изучения, а проект помечен как MIT в `pyproject.toml`.

### Почему доверие пока должно быть ограниченным

- версия 0.10.8 имеет статус **beta**;
- независимый аудит безопасности и формальная сертификация не проводились;
- текущая архитектура Core гибридная: Go отвечает за службу, single-instance, watchdog и локальный proxy, а функциональный API `/v1` продолжает выполняться Python compatibility engine на закрытом loopback-порту;
- встроенного сквозного клиентского шифрования файлов сейчас нет;
- содержимое файлов не шифруется самим Cloud Storage на физическом диске;
- сервер и его администратор технически имеют доступ к содержимому файлов;
- защита от потери данных зависит от исправности компьютера, дисков, электропитания и настроенных резервных копий;
- интернет-доступ через Cloudflare или zrok2 добавляет внешнего инфраструктурного посредника;
- мобильные приложения отстают от Desktop-линии и требуют отдельной проверки перед публичным магазинным релизом;
- в репозитории указана лицензия MIT, но отдельный файл `LICENSE` пока отсутствует — его следует добавить до публичного юридического заявления об условиях использования кода.

SHA-256 подтверждает целостность, но не скрывает содержимое. DPAPI защищает локальный токен клиента, но не шифрует пользовательские файлы на сервере.

## Как безопасно использовать систему сейчас

Для практического использования рекомендуется:

1. Выделить отдельную учётную запись ОС и регулярно обновлять Windows или Linux.
2. Включить BitLocker, LUKS или другое полнодисковое шифрование на серверных накопителях.
3. Не публиковать административные порты и Manager API в интернет.
4. Для удалённого доступа использовать HTTPS через VPN, Cloudflare Tunnel, zrok2 или корректно настроенный собственный reverse proxy.
5. Использовать уникальные пароли и своевременно отзывать потерянные устройства.
6. Хранить минимум одну независимую резервную копию на другом физическом носителе.
7. Периодически проверять восстановление, а не только наличие папки backup.
8. Не считать публичную ссылку приватной после отправки другому человеку.
9. Не хранить единственную копию критически важных документов в beta-версии.
10. Перед серьёзным использованием провести собственное тестирование под реальной нагрузкой.

## Что Cloud Storage не делает

- не предоставляет собственный центральный дата-центр;
- не загружает все файлы разработчику проекта;
- не даёт гарантированный SLA доступности;
- не заменяет резервное копирование;
- не использует SMB/WebDAV/FTP как основной канал данных;
- не включает встроенное end-to-end шифрование пользовательских файлов;
- не делает домашний сервер автоматически неуязвимым;
- не может защитить данные, если злоумышленник полностью контролирует сам сервер или учётную запись администратора ОС.

## Приватность

При локальном использовании данные и метаданные остаются на сервере владельца. Проект не требует центральной базы аккаунтов Cloud Storage для обычной работы.

При включении сторонних функций соответствующие данные проходят через выбранного провайдера:

- Cloudflare Tunnel или zrok2 передаёт сетевой трафик через инфраструктуру провайдера;
- SMTP/Gmail получает письмо и вложение, которое отправляет администратор;
- Telegram получает текст настроенных уведомлений;
- webhook получает данные, явно предусмотренные интеграцией.

Поэтому приватность зависит не только от Cloud Storage, но и от включённых интеграций, операционной системы и политики выбранного провайдера.

## Совместимость

- Сервер и Desktop Client: основной фокус — Windows.
- Виртуальные диски Windows: WinFsp.
- Серверный код и часть клиента могут запускаться на Linux/macOS из исходников, но готовность упаковки и системных интеграций отличается от Windows.
- Android: APK/AAB предусмотрены мобильным проектом.
- iPhone/iPad: исходный проект и Simulator-сборка предусмотрены; для физического устройства нужна подпись Apple Developer.
- Мобильная линия сейчас старше по архитектуре и ниже по версии, чем Desktop beta.

## Частые вопросы

### Нужен ли постоянный интернет?

Нет. В локальной сети сервер и клиент могут работать без внешнего интернета. Интернет нужен для удалённого доступа, получения обновлений и сторонних интеграций.

### Где хранятся мои файлы?

На физических накопителях, которые администратор назначил в Server Manager. Внутри управляемого корня файлы лежат как непрозрачные объекты, а пользовательские имена и структура хранятся в метаданных.

### Может ли разработчик увидеть мои файлы?

При полностью локальной установке проект не отправляет файлы в центральное облако разработчика. Но доступ к данным имеют администратор самого сервера, операционная система и любые включённые внешние провайдеры на своём участке передачи.

### Что произойдёт при отключении интернета?

Локальный доступ продолжит работать, если сервер доступен в домашней сети. Удалённый доступ и внешние уведомления временно прекратятся. Desktop Client сохраняет очередь передач и локальный кэш для последующего восстановления соединения.

### Что произойдёт при выходе из строя основного диска?

Если настроен доступный резервный storage root, новые файлы могут направляться туда. Уже существующие файлы будут доступны только при наличии исправной зеркальной или резервной копии. Сам факт настройки второго диска не гарантирует копию каждого ранее записанного файла.

### Зашифрованы ли файлы?

HTTPS шифрует передачу по сети. Токены клиента защищаются системным хранилищем секретов. Но встроенного шифрования содержимого файлов на диске или end-to-end шифрования в текущей версии нет. Для защиты выключенного или украденного сервера следует включить BitLocker/LUKS.

### Можно ли подключиться с любого места?

Да, если владелец заранее настроил безопасный публичный HTTPS-вход через VPN, Cloudflare Tunnel, zrok2 или собственный домен. Один только пяти-минутный код не создаёт сетевой маршрут до компьютера: он передаёт уже доступные адреса сервера.

### Зачем нужен пяти-минутный код?

Он упрощает первое подключение и передаёт клиенту адреса и параметры доверия без ручного ввода IP. После pairing устройство использует собственный отзываемый токен, поэтому новый код при каждом запуске не требуется.

### Почему виртуальный диск не показывает реальный физический путь?

Это намеренное разделение. Пользователь получает логическое пространство и видит только разрешённые данные. Core сам выбирает физический storage root и может переносить объекты без изменения пользовательского пути.

## Текущий статус продукта

Cloud Storage развивается как beta-продукт. Версия 0.10.8 beta 2 уже объединяет сервер, Desktop Client, веб-доступ, виртуальные диски, пользователей, пространства, права, передачи, общие ссылки, обновления, диагностику и резервные операции. Однако перед стабильным выпуском 1.0 необходимы длительные испытания обновлений, отказов диска, восстановления, интернет-доступа, многопользовательской работы и безопасности.

**Cloud Storage — ваше личное облако на собственном компьютере: файлы, пользователи, веб-доступ и виртуальные диски без обязательного хранения данных у чужого провайдера.**

### Короткое описание

Cloud Storage превращает компьютер и подключённые к нему HDD или SSD в личное облако. Управляйте пользователями и правами через Server Manager, подключайте пространства как диски в Проводнике, работайте через Desktop Client или браузер и при необходимости включайте защищённый доступ из интернета. Данные остаются на выбранном вами сервере, а загрузки, переносы и обновления проходят проверку целостности.

### Честная пометка рядом с кнопкой скачивания

**Beta:** продукт подходит для тестирования и некритичных данных. Перед использованием храните независимую резервную копию. Встроенного end-to-end шифрования файлов пока нет.

### Главный экран сайта

**Собственное облако. Собственные диски. Ваши правила.**

Храните файлы на своём компьютере, подключайтесь через приложение или браузер, создавайте отдельные пространства для семьи и команды и управляйте доступом без обязательной передачи всей библиотеки стороннему облачному сервису.

### Призыв к действию

Установите Cloud Storage Server на компьютер с вашими дисками, получите пяти-минутный код подключения и откройте своё пространство в Desktop Client или браузере.
