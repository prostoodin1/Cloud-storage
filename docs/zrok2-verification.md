# Исправления zrok2 и интернет-подключения

Проверено 2026-09-03. База: Cloud Storage 0.9.20, ветка `codex/fix-zrok2`.
Это изменения исходников, не опубликованный релиз и не обновление установленной службы.

## Найдено и исправлено

- Динамический pairing создавал устройство без пароля, но интернет-шлюз требовал парольную сессию. Метод подключения теперь записан в БД: доверенные dynamic-устройства работают по своему криптографически случайному токену. Проверки активности пользователя, отзыва устройства и файловых прав сохраняются. Для legacy-устройств дополнительная парольная сессия остаётся обязательной.
- Миграция 19 переносит ранее подключённые dynamic-устройства только при наличии соответствующей записи аудита. Отсутствие пароля само по себе не даёт разрешения на беспарольный интернет-вход.
- Вызов `zrok2 enable` использует `--headless`. Manager не блокирует интерфейс во время запроса. Ошибки и таймауты не содержат enable-токен. Профиль zrok хранится отдельно в каталоге Core и используется при последующем запуске службы.
- `share public --headless --force-local` исключает передачу владения процессом стороннему zrok-agent. Повторные вызовы start не создают дубликаты, выход/остановка снимает опубликованный адрес.
- Из журнала принимается только сообщение zrok о frontend endpoints. Ссылки API/документации не считаются рабочим входом.
- Реальный hosted zrok2 вернул hostname вида `<имя>.shares.zrok.io` без схемы. Добавлено распознавание этого формата с обязательным HTTPS и последующей проверкой ответа Core. Учтены оба домена `share.zrok.io` и `shares.zrok.io`.
- До статуса online выполняется HTTPS-запрос через публичный адрес и проверяется идентификатор текущего экземпляра Core. Проверка повторяется; после трёх неудач туннель перезапускается. Это проверка полного маршрута с машины сервера, а не гарантия доступности из любой внешней сети.
- Client и Windows drive helper отправляют документированный `skip_zrok_interstitial`, чтобы получать API/файлы вместо промежуточной HTML-страницы zrok.
- При сохранении интернет-подключения Client больше не подставляет старый TLS pin локального сервера вместо пустого pin. Проверка публичного сертификата остаётся включённой.
- Проверяемый загрузчик GitHub используется также при установке zrok2; SHA-256 пакета проверяется до замены исполняемого файла.

## Проверки

- Полный Python-набор: **164 passed**, одно предупреждение совместимости Starlette/httpx.
- Windows Go drive helper: `go test ./...` успешно, включая API/upload/download с zrok-заголовком.
- Ruff и проверка diff: без ошибок.
- Официальный zrok2 2.0.4 скачан в изолированный рабочий каталог, хеш проверен, команды `version`, `share public --help`, `enable --help` выполнены.
- На установленной рабочей службе обнаружены `zrok_enabled=false`, `remote_enabled=false`; zrok2 и профиль аккаунта в каталоге рабочей службы отсутствуют. Служба не изменялась и остаётся Running.

## Реальный интернет-тест

Настоящий pairing/upload/download через hosted zrok2 **выполнен успешно**. Сценарий завершился с кодом 0. Подтверждены:

- подключение отдельного окружения аккаунта командой zrok2 enable;
- полный HTTPS-маршрут через публичный frontend до нужного экземпляра Core;
- динамический pairing без пароля и чтение разрешённых пространств;
- загрузка и скачивание 262144 байт с совпадением SHA-256;
- новый экземпляр ClientApi со сохранённым токеном устройства без повторного pairing;
- HTTP 404 для административного API через публичный frontend;
- HTTP 403 после отзыва тестового устройства;
- завершение тестового Core и отключение временного окружения zrok2; файл environment.json удалён, процессов zrok2 не осталось.

Тестовый клиент работал на том же компьютере, но обращался по публичному HTTPS-адресу через hosted zrok2, не по loopback. Попытка независимой проверки внешним веб-инструментом была остановлена политикой открытия временных адресов этого инструмента; это не свидетельствует о недоступности сервера. Работа из отдельной мобильной сети пока не подтверждена.

Изолированный сценарий находится в `work/zrok_live_test.py`, результат — `work/zrok-internet-test/live-results.json`. Он поднимает отдельный Core с временными данными, подключает отдельное окружение zrok2, проверяет вход без пароля, передачу 256 КиБ и SHA-256, повторное использование токена, скрытие Manager API и отзыв устройства. Затем останавливает тестовый Core и отключает только созданное тестовое окружение аккаунта.

Не выполнены выпуск установщиков, установка исправлений в рабочую службу и проверка с отдельного компьютера/мобильной сети. Android не менялся.

## Проверка браузером: просмотр файлов как в Google Drive

Отдельно открыт корень публичного адреса временного Core во встроенном браузере. Появилась страница уведомления zrok с кнопкой `Visit Share`. После нажатия и повторного чтения страницы уведомление осталось; до интерфейса Cloud Storage браузер не дошёл. Сертификатные предупреждения не обходились, заголовки и cookies браузера вручную не подменялись.

Независимо от этого препятствия, проверка маршрутов Core подтверждает отсутствие полноценного веб-клиента: `GET /` возвращает служебный JSON (`service`, `status`, `version`, `health`), а `/v1/public/shares/{token}` — JSON-описание общей ссылки. Есть API файлов и скачивание по отдельным ссылкам, но нет HTML-страницы входа, списка пространств/папок и браузерных элементов загрузки/скачивания.

Итог: сценарий «открыть сервер браузером, войти и работать с файлами как в Google Drive» сейчас **не реализован и проверку не прошёл**. Успешный API-тест выше нельзя считать подтверждением браузерного сценария. Для нужного поведения необходим веб-клиент с безопасным входом и проверкой прав через существующий Core. В этом проходе проводилась диагностика, веб-клиент не добавлялся.

Для постоянного автоподключения после перезапуска туннеля требуется зарезервированное имя zrok2 (`zrok2 create name -n public <имя>`) и его указание в Manager. У ephemeral-туннеля адрес меняется; без сервиса поиска серверов старый адрес автоматически восстановить нельзя. В Manager добавлено соответствующее предупреждение. Первый вход также требует включённого разрешения на погашение кодов через интернет.

Официальные источники форматов команд/вывода: [zrok2 share public](https://github.com/openziti/zrok/blob/v2.0.4/cmd/zrok2/sharePublic.go), [enable](https://github.com/openziti/zrok/blob/v2.0.4/cmd/zrok2/enable.go), [HTTP frontend](https://github.com/openziti/zrok/blob/v2.0.4/endpoints/publicProxy/http.go).
