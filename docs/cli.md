# CLI для ИИ и автоматизации

CLI поставляется отдельно с b6 и дополняет графические Client и Server Manager. Он использует текущий
Cloud Storage API v1; tus, SFTP, S3 и переключение протоколов здесь ещё не реализованы.

CLI не импортирует Qt, не открывает окна, не задаёт вопросов и не запускает
локальную/облачную модель. Его можно вызывать из любого ИИ-инструмента как обычный
процесс. Вывод по умолчанию — один JSON-документ в stdout, `schema_version: 1`.
`--json` допускается для явного указания этого режима. `--help` выводит текстовую справку.
Общие параметры указываются перед именем команды.

## Запуск

Из исходников:

```powershell
.venv\Scripts\python.exe -m cloud_storage.cli capabilities
.venv\Scripts\python.exe -m cloud_storage.cli health
```

После установки Python-пакета доступна команда `cloud-storage`. Отдельный Windows EXE
собирается через `scripts/build-cli.ps1`; Python на целевом ПК ему не нужен.
Готовый EXE доступен в [релизе b6](https://github.com/prostoodin1/Cloud-storage/releases/tag/v0.10.8b6).
При публикации стандартным `scripts/publish-release.ps1` добавьте `-IncludeCLI` и
поместите `CloudStorageCLI.exe` в выбранный `OutputDirectory` вместе с остальными пакетами.

```powershell
CloudStorageCLI.exe capabilities
CloudStorageCLI.exe --server https://example.net health
CloudStorageCLI.exe doctor --local
CloudStorageCLI.exe --server https://example.net spaces
CloudStorageCLI.exe --server https://example.net ls SPACE_ID "Документы"
CloudStorageCLI.exe --server https://example.net upload SPACE_ID "D:\file.bin" "Документы/file.bin" --state "D:\qa-upload.json"
CloudStorageCLI.exe --server https://example.net upload-status "D:\qa-upload.json"
CloudStorageCLI.exe --server https://example.net download SPACE_ID "Документы/file.bin" "D:\download.bin"
```

## Авторизация

Для файловых операций требуется токен уже одобренного устройства в переменной
`CLOUD_STORAGE_DEVICE_TOKEN`. ИИ-процесс должен получить её из защищённого окружения
или хранилища секретов. Имя переменной можно изменить через `--token-env NAME`.
Параметра с самим токеном нет: он не должен попадать в список аргументов процесса.
CLI не выводит токен и не записывает его в checkpoint. Новое устройство автоматически
не регистрируется, права пользователя не повышаются.

Для сертификата из приглашения используйте `--fingerprint SHA256`. Проверка
сертификата не отключается. HTTP разрешён только для loopback-адресов; внешние
подключения требуют HTTPS. Перенаправления на другие серверы CLI не использует.

`doctor --local` читает уже существующие локальные `core-config.json` и
`core-secrets.json`, не создаёт ключей и не меняет конфигурацию. Другой каталог
можно явно указать через `--core-data-dir`. Нужны права чтения этих файлов.
Сервер выполняет проверку дисков в собственном контексте службы, включая порог
заполнения и недоступные накопители. Это проверка доступности/ёмкости, а не
доказательство успешной записи или исправности оборудования.

Без `--local` команда `doctor` требует manager-токен через выбранную переменную
окружения и доступ к административному API. Этот API не следует публиковать наружу.
Старое ядро b5 не имеет `/v1/admin/storage-readiness`: диагностика требует ядра
b6 или новее. `health`, списки и передачи используют прежний API v1.

## Докачка и ошибки

Повторите ту же команду `upload` с тем же `--state`: CLI заново проверит исходный
файл, получит фактическое смещение с сервера и продолжит загрузку. После потери
ответа клиент не предполагает, что блок не дошёл. Checkpoint сохраняется также
после успеха, чтобы повтор команды не создавал ещё одну версию файла.

Без `--state` checkpoint хранится в `%LOCALAPPDATA%\CloudStorageCLI\uploads`
(на других ОС — `~/.cache/CloudStorageCLI/uploads`). На один checkpoint действует
межпроцессная блокировка. `--restart` явно начинает новую upload-сессию.
Создание сессии после потерянного ответа автоматически не повторяется; на сервере
может остаться незавершённая сессия до её истечения. Перенос checkpoint не переносит
токен или права. После истечения/удаления серверной сессии бесшовная докачка не обещается.

Скачивание получает SHA-256 из каталога, продолжает существующий `.part` и проверяет
хеш. Уже существующий конечный файл заменяется только с `--overwrite`.
Публикация загруженного файла под существующим именем подчиняется правам API:
при наличии `can_modify` это создаёт новую версию. Для загрузки используйте явно
выбранное назначение, чтобы ИИ не менял чужой файл по ошибке.

По умолчанию предусмотрены 3 повторные попытки временных сетевых ошибок и deadline
передачи 3600 секунд. Настройки: `--retries 0..8`,
`--transfer-timeout 1..604800`, `upload --chunk-mib 1..64`.
Фактический блок ограничивается также лимитом сервера. Deadline проверяется между
блоками и опросами завершения; уже начатый HTTP-запрос может ждать своего timeout.
Ошибки доступа, сертификата и ёмкости не повторяются автоматически.

| Код процесса | Значение |
|---|---|
| 0 | Успех |
| 1 | Непредвиденная ошибка клиента, без traceback и секретов в stdout |
| 2 | Неверные параметры/несовместимый checkpoint |
| 3 | Нет авторизации, прав или не прошла проверка сертификата |
| 4 | Ошибка API/сети либо deadline передачи |
| 5 | Недостаточная ёмкость/квота; либо doctor показал `ready: false` |
| 6 | Конфликт состояния/занятый checkpoint |
| 7 | Ошибка локального файла/checkpoint |
| 130 | Прерывание пользователем |

Ошибка обычно имеет поля `error.code`, `error.http_status`, `error.retryable`.
`doctor` при недостаточной готовности возвращает данные проверки в `data`, `ok: false`
и код 5. Потребитель всегда должен проверить и код процесса, и поле `ok`.

## Изменения ядра

- Файл, завершённая передача и завершённая upload-сессия фиксируются одной
  SQLite-транзакцией после переноса данных.
- После прерывания между rename и транзакцией завершение проверяет сохранённый
  объект по размеру/SHA-256 и повторяет фиксацию без новой версии файла.
- Ошибка после успешной фиксации не удаляет уже опубликованные данные.
- Старая сессия не подтверждает более новую версию, записанную под тем же именем.
- Недоступный диск при уборке не мешает запуску ядра; HTTP-ошибки I/O возвращаются
  как 503, заполнение диска как 507. Состояние готовности диагностируется отдельно
  от доступности процесса.

Это не полная перепись ядра и не гарантия отсутствия любых ошибок. Проверки
аварийного завершения процесса не равны проверкам отключения питания или отказа
носителя. Установленную службу пользователя разработческие тесты не заменяют.
