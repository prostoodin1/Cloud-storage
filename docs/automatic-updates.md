# Автоматическое обновление Windows-приложений

Клиент и Server Manager используют общий механизм обновлений. Изменения ниже
включены в b5; установщики b4 их не содержат.

## Что происходит при запуске

1. Через 1,5 секунды после запуска собранного приложения начинается фоновая проверка
   подписанного каталога. Работа программы не блокируется сетевым запросом.
2. Более новая версия скачивается с проверкой размера и SHA-256. Неполную загрузку
   можно продолжить при следующей попытке; полный проверенный пакет используется повторно.
3. Во время передач установка откладывается. Готовность проверяется каждые 30 секунд.
   Клиент также ждёт завершения своих фоновых операций. Manager запрашивает текущее
   число серверных передач, включая записи за пределами страницы истории.
4. Запускается установщик в тихом режиме. Windows может запросить права администратора.
   После установки приложение запускается снова. Автоматической перезагрузки ПК нет.

Состояние обновления видно в строке состояния и разделе «Обновления». Для нового
профиля режим по умолчанию — автоматическая установка. Бета-сборка получает стабильные
и тестовые версии, стабильная сборка — только стабильные. Явно сохранённый ручной режим
и выбранный канал сохраняются. Повреждённый файл настроек включает ручной режим.

При недоступном интернете приложение продолжает работать. Отмена запроса UAC
не закрывает приложение и не останавливает Core. Повторного автоматического запроса
прав в этом запуске нет; установку можно повторить кнопкой или при следующем запуске.
Если Manager не может подтвердить отсутствие серверных передач, установка откладывается;
остаётся ручная кнопка установки. Проверка готовности не резервирует сервер от новых
подключений: клиент может начать передачу между проверкой и остановкой службы.

Сам установщик останавливает серверные компоненты после получения прав. Обновление
не заменяет резервное копирование базы и файлов. Запуск из исходников и `--smoke-test`
не запускают автоматическую проверку. Этот сценарий относится к Windows Client
и Server Manager; приложения Android/iOS и отдельные headless-службы в него не входят.

## Публикация версии

Одной публикации Setup в GitHub Release недостаточно: версия должна появиться в
подписанных каталогах обоих продуктов. Начиная с b5 используются отдельные файлы
`cloud-storage-client-catalog-v2.json` и `cloud-storage-server-catalog-v2.json`.
Старые каталоги и их доверенный ключ не меняются: прежний приватный ключ на этом
ПК недоступен, поэтому существующие приложения не смогут сами обнаружить b5
через прежний канал. Для перехода нужен один запуск versioned Setup b5.

При выпуске новой версии используйте `scripts/publish-release.ps1`: он создаёт
подписанные манифесты установщиков, объединяет их с прежними каталогами и обновляет
каталоги на стабильном релизе, который обслуживает адрес `releases/latest/download`.
Приватный ключ v2 хранится в `%LOCALAPPDATA%\CloudStorageRelease\update-signing-v2.dpapi`:
Windows DPAPI шифрует его для текущего пользователя, ACL ограничивает доступ.
Сценарии подписания расшифровывают ключ в памяти; открытый PEM-файл не создаётся.
Приватный ключ не включается в репозиторий или установщики. Для восстановления
опубликованного prerelease предназначен `scripts/repair-release-catalogs.ps1`.

После публикации следует вызвать `UpdateService.list_versions("beta")` отдельно
для `client` и `server`, проверить версию, канал и URL Setup, а затем выполнить
установку и повторный запуск на отдельной Windows-машине/VM. Тесты с подменённым
запуском установщика не подтверждают реальную установку через UAC.

Существующую установку необходимо один раз обновить полным Setup b5. Если был явно
сохранён ручной режим, включите автоматическую установку в разделе «Обновления».
Дальнейшие версии будут обнаруживаться через подписанный канал v2.
