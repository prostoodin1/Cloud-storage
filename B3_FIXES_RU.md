# Cloud Storage: исправления для подготовки b3

Дата: 27 октября 2026. База: `2df2327266cff79b14227b60651c99828f425e05`, ветка `codex/transfer-performance-resilience`.

Это локальный кандидат для проверки. Внутренняя версия пока `0.10.8b2`: релиз b3 не опубликован, установленный сервер не заменён. Ранее измеренные скорости находятся в `PERFORMANCE_REPORT_RU.md`; новых измерений пропускной способности в этой итерации нет.

## Проверки

- Полный Python-прогон: **251 passed**, 105,40 с. Одно предупреждение об устаревшей интеграции Starlette/httpx.
- После финальной правки повреждённого временного файла: целевые тесты клиента и скачивания — **29 passed**.
- Ruff: проверка Python-кода, тестов и валидатора каталогов пройдена.
- Мобильные протокольные проверки: **10/10**. TypeScript `tsc --noEmit` пройден.
- Экспорт JavaScript/Hermes для Android и iOS пройден. Это не сборки APK/IPA и не испытание на телефонах.
- Windows Client и LegacyCore пересобраны. Native Go Core, Service, Managers и WinFsp-компонент взяты из исходной беты без изменений.
- Проверка готового Windows-комплекта через Native Go Core: **27/27**, включая Range, If-Range, публичный диапазон, авторизацию, перезапуск и сохранение файлов/сессии.
- Настоящее монтирование виртуального диска Windows: **7/7**, включая создание файла и совпадение SHA-256 после передачи.
- Python-клиент отдельно проверен через настоящий HTTP-сокет: догрузка, уже полностью полученный временный файл, повреждённый временный файл, отказ при смене содержимого на сервере.

Изолированные тесты использовали отдельные каталоги и свободные порты. Рабочая служба не заменялась. Тестовые каталоги могут содержать служебное состояние; в архив кандидата они не включены.

## Что ещё отделяет от выпуска b3

1. Пересобрать нативные мобильные приложения: добавлен `expo-sqlite`, одного обновления JavaScript недостаточно. Проверить Android/iOS на реальных устройствах: фон, принудительное завершение, сон, переключение Wi-Fi/сотовой сети, заполненный диск и большие файлы.
2. Проверить передачу между независимыми устройствами через интернет: разные задержки, потери, NAT, прямой и промежуточный маршрут, несколько клиентов. В этой итерации такой стенд отсутствовал.
3. Выполнить длительный нагрузочный прогон и измерить CPU, RAM, диск, восстановление после обрывов. Модельные тесты аренды не доказывают поведение планировщика мобильной ОС.
4. Для цели **100–200 МБ/с** нужны как минимум **800–1600 Мбит/с полезной пропускной способности** по всему пути, плюс запас на протоколы. Эти исправления улучшают восстановление и целостность, но достижение указанной скорости не доказано. Хеширование мобильного файла выполняется в JS и требует замеров на слабых устройствах.
5. Перед выпуском согласованно поднять версии компонентов, подготовить установщики и подписи, проверить обновление со старой версии. Каталоги клиента/сервера публикуются последовательно: восстановление реализовано, глобальной атомарной транзакции GitHub и защиты от двух одновременных ручных издателей нет.

Состояние профиля мобильного приложения по-прежнему сохраняется в JSON; в SQLite перенесены контрольные точки очереди и владение заданиями. Гарантия отсутствия любых падений не заявляется.
