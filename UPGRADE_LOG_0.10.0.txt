CLOUD STORAGE 0.10.0 — СТАБИЛЬНАЯ БАЗОВАЯ ЛИНЕЙКА
===================================================

Статус документа: финальное техническое задание для реализации другим ИИ-агентом.
Версия продукта: 0.10.0.
Следующие исправления после выпуска должны называться 0.10.1, 0.10.2 и так далее.


1. ГЛАВНАЯ ЦЕЛЬ
================

Нужно перестроить Cloud Storage вокруг одного надёжного сценария:

1. Server Manager запускает ровно один экземпляр Core.
2. Core каждые 5 минут создаёт единый динамический код подключения.
3. Один и тот же код принимают Desktop Client и браузер.
4. После первого подключения устройство получает собственный постоянный защищённый токен.
5. Desktop Client запоминает подключение и в дальнейшем входит автоматически.
6. Браузер после ввода кода получает защищённую серверную сессию в cookie.
7. Desktop Client и браузер видят одни и те же разрешённые файлы и папки.
8. Пользователь может создавать папки, загружать, скачивать, переименовывать и удалять файлы.
9. Подключение работает в локальной сети и через постоянный публичный HTTPS-адрес Cloudflare Tunnel.
10. Перезапуск Manager, Core или компьютера не теряет файлы, пользователей, устройства, токены и настройки.

Это вертикальный рабочий срез. Дополнительные протоколы и сложные подсистемы не должны мешать этому сценарию.


2. ОБЯЗАТЕЛЬНЫЕ АРХИТЕКТУРНЫЕ ПРАВИЛА
=====================================

2.1. Единственный Core
----------------------

- На компьютере одновременно должен работать максимум один Core.
- Manager, Windows-служба и установщик обязаны использовать один каталог конфигурации и одну базу данных.
- Core должен иметь процессный lock с PID, временем запуска и идентификатором экземпляра.
- Устаревший PID нужно безопасно удалять только после проверки, что процесс действительно не относится к Cloud Storage.
- Нельзя одновременно запускать Python Legacy Core и Go Core как два независимых сервера.
- Если Go Core является supervisor, он должен владеть жизненным циклом совместимого API-процесса и предоставлять единый статус.
- Manager не должен показывать «Сервер работает», пока обязательный health-check API не вернул успешный ответ.

2.2. Единственный API
---------------------

- Desktop Client и браузер используют один HTTPS API.
- Основные файловые операции не должны иметь отдельные несовместимые реализации для браузера и Desktop Client.
- Локальное и интернет-подключение отличаются только сетевым маршрутом, но не форматом запросов и правами.
- API должен возвращать локализованные безопасные ошибки без Python traceback, Pydantic-структур и внутренних путей.

2.3. Один источник настроек
--------------------------

- Настройки Core хранятся в одном атомарно записываемом конфигурационном файле либо в базе данных.
- Manager не должен иметь отдельную копию сетевых настроек, расходящуюся с Core.
- Изменения настроек должны сохраняться через административный API Core.
- Установщик и обновление обязаны сохранять прежние данные и выполнять миграции.

2.4. Один сетевой маршрут для интернета
---------------------------------------

- Основной публичный транспорт 0.10.0 — Cloudflare Tunnel.
- zrok/zrok2, ручной проброс портов, WebDAV, SMB, FTP, SFTP и SSH не участвуют в основном сценарии 0.10.0.
- Старый код можно оставить в репозитории для миграции, но функции должны быть скрыты и не запускаться автоматически.
- Публичный URL Cloudflare должен сохраняться и отображаться в Manager.
- При недоступности Cloudflare локальное подключение продолжает работать.


3. УНИВЕРСАЛЬНЫЙ ДИНАМИЧЕСКИЙ КОД
=================================

3.1. Поведение
--------------

- Core автоматически создаёт новый код каждые 5 минут.
- Пример отображаемого кода: A7K9-4Q2M-X8P3.
- Один и тот же текущий код можно ввести в Desktop Client или браузере.
- Код используется только для первоначальной привязки устройства или браузерной сессии.
- Уже подключённые устройства не отключаются после смены кода.
- Просроченный код отклоняется.
- Неверный код отклоняется одинаково в Desktop Client и браузере.
- Количество попыток ограничивается по IP и по Server ID.
- Новый пользователь или устройство получает минимальные обычные права, но не права администратора.

3.2. Содержимое и защита
-----------------------

Код должен криптографически защищать следующие сведения:

- версия формата;
- Server ID;
- основной публичный HTTPS-адрес;
- список запасных локальных HTTPS-адресов;
- порт при необходимости;
- время выпуска;
- время истечения;
- криптографически случайный nonce;
- идентификатор целевого пользователя, если код создан для существующего пользователя;
- подпись или MAC, позволяющие обнаружить любое изменение данных.

Секрет подписи не передаётся клиенту и не хранится в открытом виде в интерфейсе.

3.3. Выбор адреса
----------------

Desktop Client должен пробовать адреса строго в таком порядке:

1. Проверенный публичный Cloudflare HTTPS URL.
2. Другой настроенный публичный HTTPS URL.
3. Локальные HTTPS-адреса.
4. Loopback разрешён только при запуске клиента на серверном компьютере.

Ошибка одного адреса не должна останавливать перебор остальных адресов.
Успешный /health без успешного pairing не считается успешным подключением.

3.4. После успешного pairing
----------------------------

- Сервер создаёт отдельную запись устройства.
- Сервер выдаёт случайный токен устройства.
- В базе хранится только безопасный хеш токена.
- Desktop Client хранит токен через Windows DPAPI или системное защищённое хранилище.
- Браузер получает HttpOnly, Secure, SameSite cookie и серверную сессию.
- Токены и сессии можно отозвать из Manager.
- Смена динамического кода не меняет ранее выданные токены.


4. SERVER MANAGER — ГЛАВНЫЕ ВКЛАДКИ
===================================

4.1. «Основная» — оставить и исправить
--------------------------------------

Показывать только подтверждённые Core данные:

- сервер запущен или остановлен;

Запрещено показывать синтетический размер 8 ТБ. Размер берётся с физического диска либо из явно заданной квоты пространства.

4.2. «Подключение» — полностью переделать
-----------------------------------------

Показывать:

- текущий универсальный пяти­минутный код;
- обратный отсчёт;
- кнопку копирования;
- QR с тем же кодом;
- локальный адрес сайта;
- публичный адрес сайта;
- кнопки «Открыть сайт» и «Копировать адрес»;
- список подключённых пользователей и устройств;
- выбор: новый пользователь или существующий пользователь.

Убрать из основного сценария:

- логин и пароль;
- старые ссылки приглашения;
- файлы доступа;
- ручной IP;
- ручной TLS fingerprint;
- отдельные коды CS1/CS2/CS3;
- разные коды для браузера и Desktop Client.

4.3. «Диски» — упростить
------------------------

Для 0.10.0 реализовать:

- выбор одной основной папки хранения;
- определение физического диска;
- реальный общий объём;
- свободное место;
- используемое Cloud Storage место;
- тест чтения и записи;
- безопасную смену каталога;
- запрет выбора системно опасных и непригодных директорий;
- сохранение выбранной папки после обновления.

Временно скрыть:

- зеркалирование;
- основной и резервный диск;
- автоматическую миграцию;
- SSD staging;
- сложную иерархию физических и логических дисков.

4.4. «Приём» и «Отправка» — объединить в «Передачи»
---------------------------------------------------

Показывать:

- направление;
- имя файла;
- пользователя;
- размер;
- прогресс;
- скорость;
- оставшееся время;
- состояние;
- понятную ошибку;
- отмену;
- повтор;
- список завершённых операций.

Передача должна корректно переживать краткий обрыв. Частичный файл не должен становиться готовым файлом до успешной проверки.

4.5. «Обновления» — оставить
----------------------------

- Проверять подписанный каталог версий.
- Показывать последнюю и доступные старые версии.
- Поддерживать автоматический выбор последней версии и ручной выбор версии.
- Проверять Ed25519-подпись каталога.
- Перед запуском проверять размер, SHA-256 и подпись установщика.
- Сохранять базу, файлы, настройки, пользователей и токены.
- При ошибке различать: нет интернета, 404, TLS, неверная подпись, неверный SHA-256 и недоступный установщик.

4.6. «Помощь» — переписать
--------------------------

Удалить или пометить устаревшими инструкции про zrok, пароли, старые приглашения и ручной IP.
Добавить актуальные инструкции:

- как запустить сервер;
- где взять пяти­минутный код;
- как подключить Desktop Client;
- как войти через браузер;
- как подключиться из интернета;
- как отозвать устройство;
- как загрузить и скачать файл;
- как выполнить диагностику.

4.7. «Система» — сократить
--------------------------

В 0.10.0 оставить:

- состояние службы и Core;
- версию и путь установки;
- сеть;
- интерфейс;
- журналы.

Скрыть и не запускать автоматически:

- питание;
- автоматизации;
- отчёты;
- Docker;
- SSH;
- контейнеры.

7. БРАУЗЕРНЫЙ КЛИЕНТ
====================

7.1. Экран входа
----------------

- Одно поле динамического кода.
- Одна кнопка подключения.
- Один и тот же код с Desktop Client.
- Сообщения: неверный код, код истёк, сервер недоступен, слишком много попыток.
- После входа код очищается из DOM и истории интерфейса.

7.2. Сессия
-----------

- Серверная случайная сессия.
- HttpOnly cookie.
- Secure для внешнего HTTPS.
- корректный SameSite;
- CSRF-токен для изменяющих запросов;
- отзыв сессии через Manager;
- сохранение сессии после перезапуска Core;
- выход удаляет сессию.

7.3. Файлы
----------

- пространства;
- папки;
- хлебные крошки;
- переход вверх;
- создание папки;
- загрузка;
- скачивание;
- переименование;
- удаление;
- квота и фактическое использование.

Автообновление не должно выбрасывать пользователя из открытой папки.

7.4. Работа за Cloudflare
-------------------------

- учитывать внешний HTTPS scheme и proxy headers;
- доверять proxy headers только от ожидаемого локального cloudflared;
- правильно формировать Secure cookie;
- проверять Origin/Host;
- не ломать большие потоковые загрузки;
- использовать понятные тайм-ауты;
- не загружать весь файл в оперативную память.


8. ФАЙЛОВЫЙ API 0.10.0
======================

Минимальные операции:

- GET /v1/health
- POST /v1/pairing/redeem
- POST /v1/web/pair
- POST /v1/web/logout
- GET /v1/spaces
- GET /v1/spaces/{space_id}/entries
- POST /v1/spaces/{space_id}/directories
- PUT или потоковый upload endpoint для файла
- GET download endpoint с поддержкой Range
- PATCH rename/move endpoint
- DELETE file/directory endpoint
- GET /v1/transfers
- административные endpoints пользователей, устройств, диагностики и настроек

Требования:

- нормализация путей;
- запрет .. и выхода за storage root;
- атомарная запись через временный файл;
- ограничение размера;
- проверка квоты;
- SHA-256;
- понятные коды ошибок;
- проверка прав в Core;
- аудит изменяющих операций;
- потоковая загрузка и скачивание;
- очистка незавершённых временных файлов.


9. ДАННЫЕ И МИГРАЦИИ
====================

- Не удалять существующие пользовательские файлы.
- Перед первой миграцией 0.10.0 создать проверяемую резервную копию SQLite.
- Сохранить Server ID, если база исправна.
- Существующих пользователей перенести без паролей в новую ролевую модель.
- Старые device tokens либо безопасно мигрировать, либо явно отозвать с понятным уведомлением.
- Старые приглашения, пароли и ссылки больше не должны приниматься основным API.
- Старые сетевые настройки zrok сохранить только для истории, но не запускать.
- Все миграции должны быть повторяемыми и транзакционными.
- При ошибке миграции Core не должен запускаться с частично изменённой базой.


10. УСТАНОВЩИКИ
===============

Должны существовать два постоянных bootstrap-файла:

- CloudStorage-Server-Installer-windows-x64.exe
- CloudStorage-Client-Installer-windows-x64.exe

Их имена не меняются с каждой версией.

Каждый установщик:

- загружает подписанный каталог;
- предлагает последнюю версию или ручной выбор;
- проверяет подпись, размер и SHA-256;
- предлагает создать ярлык на рабочем столе;
- обновляет существующую установку;
- сохраняет пользовательские данные;
- не создаёт дубликаты службы и процессов;
- показывает локализованную причину ошибки.

Server Installer дополнительно:

- создаёт резервную копию базы;
- устанавливает или обновляет одну Windows-службу;
- сохраняет storage root;
- исправляет firewall rule без создания дублей.

Client Installer дополнительно:

- сохраняет защищённые подключения;
- не требует повторного pairing после обычного обновления.


11. ЧТО НЕ ВХОДИТ В 0.10.0
==========================

Не реализовывать и не чинить в этом выпуске:

- мобильные приложения;
- Docker и контейнеры;
- SSH;
- автоматизации;
- питание и Wake-on-LAN;
- Telegram/Gmail/SMTP;
- отчёты;
- SMB, FTP, SFTP, WebDAV;
- zrok/zrok2;
- SSD staging;
- зеркала и резервные диски;
- сложные резервные копии;
- офлайн-синхронизацию;
- виртуальный диск Windows.

Код этих функций можно сохранить, но они должны быть скрыты, выключены по умолчанию и не влиять на Core.


12. ОБЯЗАТЕЛЬНАЯ МАТРИЦА ПРОВЕРКИ
================================

12.1. Один компьютер

- чистая установка Server;
- запуск Core;
- вход браузером по коду;
- вход Desktop Client по тому же коду;
- создание папок;
- загрузка и скачивание;
- совпадение SHA-256;
- перезапуск Core;
- сохранение файлов и входов.

12.2. Два компьютера в одной LAN

- сервер на первом компьютере;
- Desktop Client на втором;
- pairing по коду без ручного IP;
- браузер на втором компьютере;
- загрузка клиентом и скачивание браузером;
- загрузка браузером и скачивание клиентом.

12.3. Разные сети через Cloudflare

- сервер в домашней сети;
- клиент через другую Wi-Fi/мобильную сеть;
- браузер через другую сеть;
- pairing одним универсальным кодом;
- загрузка и скачивание минимум 1 МБ, 100 МБ и 1 ГБ;
- временный разрыв сети;
- автоматическое восстановление;
- проверка отсутствия доступа к административному API.

12.4. Безопасность

- поддельный код;
- просроченный код;
- повторные попытки brute force;
- отозванное устройство;
- заблокированный пользователь;
- обход пути через ../;
- прямой API-запрос без права;
- CSRF;
- неверный Origin;
- попытка получить файл другого пользователя;
- отсутствие токенов и секретов в логах.

12.5. Обновление

- обновление с последней стабильной версии 0.9.x;
- сохранение файлов;
- сохранение Server ID;
- отсутствие двух служб;
- отсутствие двух Core;
- возможность отката через установщик;
- понятное сообщение при несовместимой базе.
