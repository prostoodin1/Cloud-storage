# Архитектура Cloud Storage Server Beta 0.2

## Граница процессов

Server Manager и Server Core — разные процессы. Менеджер показывает состояние дисков и отправляет административные команды через локальный API. Core владеет базой, пользователями, устройствами и файловыми операциями; закрытие окна менеджера его не останавливает.

Основные слои:

1. `ui/` — интерфейс PySide6 без прямой записи пользовательских файлов.
2. `services/disk_service.py` и `settings_store.py` — обнаружение устройств и атомарные настройки менеджера.
3. `services/core_client.py` — локальный клиент API и запуск отдельного процесса Core.
4. `core/api.py` — версионированный HTTP API v1 и границы авторизации.
5. `core/repository.py` — пользователи, пространства, приглашения, устройства и аудит.
6. `core/storage.py` — маршрутизация, квоты, версии и атомарные файловые операции.
7. `core/database.py` — SQLite со строгими внешними ключами, WAL и синхронной фиксацией.

## Личное пространство

Создание пользователя и пространства «Мои файлы» выполняется одной транзакцией. Пространство имеет владельца и квоту. Логический путь клиента никогда не превращается напрямую в физический: содержимое хранится под случайным идентификатором объекта, а соответствие пути и версии находится в SQLite.

Загрузка сначала пишется в `.staging`, одновременно подсчитываются размер и SHA-256. После повторной проверки квоты в транзакции файл атомарно переносится в `objects`. Предыдущая версия остаётся учтённой, а удаление перемещает объект в `.trash` и помечает запись удалённой.

## Подключение устройства

Менеджер создаёт одноразовое приглашение с ограниченным сроком. Клиент обменивает код и пароль на токен ожидающего устройства. До ручного подтверждения администратора токен позволяет читать только статус сопряжения. Подтверждённый токен открывает доступ лишь к пространствам своего пользователя; отзыв действует немедленно.

## Физические диски

Менеджер передаёт ядру только доступные активные диски с ролями общего, личного или дополнительного хранилища. Core создаёт внутри точки монтирования отдельный управляемый каталог и маркер собственности. Непустые каталоги без маркера не принимаются. При выборе корня учитываются приоритет, предел заполнения и минимальный свободный резерв; один файл всегда целиком находится на одном корне.

## Служба и API

Core поставляется как отдельный исполняемый файл, Windows Service Host и пользовательская systemd-служба. Административный HTTP-вход всегда привязан к loopback-интерфейсу. Параллельно могут работать LAN HTTPS-listener с UDP-обнаружением, прямой удалённый HTTPS-listener и отдельный HTTP backend для zrok, привязанный только к `127.0.0.1`. Все клиентские входы скрывают административные маршруты; внешние входы используют строгий белый список точных клиентских путей и отклоняют всё неизвестное. Прямые HTTPS-входы используют постоянную TLS-идентичность; наружу передаётся только публичный SHA-256-отпечаток.

Удалённый listener запускается только после явного подтверждения в Manager. Публичный URL используется для приглашения, но Core не настраивает DNS, VPN, NAT, UPnP или firewall. Удалённое погашение кодов — отдельный временный флаг. Middleware ограничивает частоту внешних запросов и записывает результат в общий аудит, который Manager показывает вместе с адресом источника.

В Alpha 0.6.0a1 добавлен первый tunnel-provider этапа 6 — `ZrokTunnelService`. Core запускает внешний бинарник без shell, следит за процессом, извлекает публичный адрес, повторяет запуск с ограниченной экспоненциальной задержкой и показывает диагностику Manager. Для обычного share используется `zrok share public`; заранее созданный reserved share можно указать по безопасному имени. Backend доступен только локально и не содержит административного API. Аккаунт zrok включается пользователем штатной командой `zrok enable`; Cloud Storage не хранит его токен и не регистрирует аккаунт автоматически.

В Alpha 0.6.0a2 провайдеры собраны в `TunnelProviderRegistry`. Реестр создаётся самим Core из разрешённых встроенных реализаций; динамический импорт стороннего Python-кода отсутствует. Каждый манифест сообщает тип и возможности провайдера, а Manager может запросить состояние или перезапустить один провайдер без остановки файлового API и остальных слушателей. Эти административные маршруты доступны только через loopback Manager API и отсекаются внешним default-deny middleware.

`SupportBundleService` формирует диагностический ZIP полностью в памяти и отдаёт его Manager вместе с SHA-256. В пакет попадают версия, обезличенные системные свойства, булевы настройки, счётчики SQLite/диагностики/активности и безопасные состояния встроенных провайдеров. Сырые база и журналы, пользовательские файлы, пути, адреса, имена, идентификаторы и секреты не читаются в архив и не записываются во временный файл на сервере.

Файловые маршруты прямого удалённого входа и zrok требуют двух прикладных факторов: отзываемый токен подтверждённого устройства и короткоживущую HMAC-сессию. Сессия выдаётся только после проверки логина из SQLite и Argon2id-пароля, привязана к конкретным user/device ID и имеет срок 24 часа. Desktop Client хранит сессию отдельно от профиля (DPAPI в Windows, `0600` в Linux), а пароль нигде не сохраняет. URL без этих данных не даёт доступа к файлам.

## Desktop Client Alpha 0.3

`client/api_client.py` не зависит от Qt и реализует pairing, пространства и возобновляемые файловые операции. Постоянная очередь хранится в `transfers.db`; сервер фиксирует смещение незавершённой загрузки в своей SQLite и принимает только следующий ожидаемый блок. `client/offline.py` ведёт отдельный индекс локальных копий и сравнивает базовый, локальный и серверный SHA-256, поэтому настоящий конфликт не приводит к тихой перезаписи. `client/settings.py` хранит коллекцию серверных профилей и активный профиль; старый одиночный формат мигрирует при первом сохранении. Каждый профиль имеет отдельный секрет: в Windows bearer-токен шифруется DPAPI, а в Linux хранится отдельным файлом с режимом `0600`. Сетевые операции выполняются в рабочем пуле, поэтому большие файлы не блокируют окно.

Интеграция Client закрепляет офлайн-каталог в Проводнике Windows либо добавляет ссылку и GTK-закладку в Linux. Автозапуск настраивается только по явному выбору пользователя; системный трей позволяет приостановить и продолжить всю очередь. Конфликтующая локальная версия перед скачиванием серверной переименовывается в отдельный файл с меткой `local-conflict`.

Клиент допускает незашифрованный HTTP только для loopback-адресов. Любой удалённый адрес обязан использовать HTTPS. При закреплении SHA-256 проверяется сертификат именно того TLS-соединения, по которому идёт запрос. Полное приглашение и QR содержат код, HTTPS-адрес и отпечаток. При использовании неаутентифицированного UDP-поиска интерфейс требует сверить отпечаток с Manager перед вводом пароля.

## Помощь и локальная база знаний

`help/knowledge.py` — общий для Manager и Client слой SQLite с версионируемыми статьями и журналом вопросов без точного ответа. Поиск использует нормализацию, ключевые слова и нечёткое совпадение; каждый найденный ответ возвращается вместе с исходной статьёй. `help/page.py` показывает только статьи своей аудитории. Компонент полностью локальный, не имеет доступа к файлам пользователя и не вызывает внешние ИИ-сервисы.

## Обслуживание хранилищ Alpha 0.4

Доступность корня для чтения отделена от разрешения новых записей. Режимы паузы и обслуживания оставляют корень доступным для скачивания, но исключают его из выбора места для загрузок. Проверяемый перенос разрешён только с такого корня на активный целевой корень.

Задание хранится в SQLite и по одному обрабатывает текущие файлы и историю версий. Объект сначала копируется во временный каталог целевого диска, синхронизируется, сверяется по размеру и SHA-256 и только затем получает постоянное имя. Ссылка в метаданных переключается условным обновлением внутри транзакции. Исходный объект не удаляется автоматически: Alpha 0.4.0a2 сохраняет его как страховочную копию до появления отдельной проверяемой очистки.

Диск с назначением `backup` не участвует в выборе корня для обычной загрузки. Резервное задание сначала создаёт согласованную SQLite-копию метаданных во временном каталоге целевого диска, затем копирует перечисленные в ней текущие объекты и версии с проверкой SHA-256. Только полностью завершённый набор вместе с `manifest.json` атомарно перемещается из `.staging` в `backups`; при ошибке временный набор удаляется.

Диск с назначением `mirror` тоже исключён из обычного распределения данных. После фиксации основной версии Core отдельно копирует её через `.staging`, сверяет размер и SHA-256 и лишь затем атомарно публикует реплику. Ошибка этой фоновой защиты не откатывает уже принятую основную загрузку: в `mirror_replicas` сохраняется состояние `stale` или `error`. Постоянное задание `mirror_jobs` повторно проверяет фактическое содержимое всех актуальных реплик и восстанавливает отсутствующие или повреждённые. Если основной корень или объект недоступен, скачивание может переключиться на реплику только при полном совпадении сохранённых версии, размера и SHA-256.

## Надёжность и диагностика Alpha 0.5

`core/diagnostics.py` отделён от файлового API и не исправляет данные скрытно. Быстрый монитор выполняется в отдельном daemon-потоке после запуска Core и затем раз в пять минут: проверяет SQLite, внешние ключи, доступность и заполнение корней, маркеры принадлежности и неуспешные постоянные задания. Полная проверка запускается администратором, последовательно читает текущие объекты, корзину, версии и актуальные зеркальные реплики и пересчитывает SHA-256.

Каждый запуск и инцидент хранятся в SQLite. Стабильный fingerprint объединяет повторные обнаружения одной причины, поэтому интерфейс показывает один инцидент со счётчиком, а не поток одинаковых сообщений. Проверка, которая больше не воспроизводит проблему, атомарно переводит инцидент в `resolved`; история остаётся доступной через административный API. Прерванные состояния `queued`/`running` при старте помечаются ошибкой и не воспринимаются как успешно завершённые.

Alpha 0.5.0a2 добавляет постоянные задания `restore_jobs`. Восстановление принимает только опубликованный завершённый снимок, повторно проверяет каждый объект из его манифеста и рассматривает текущие файлы и историю версий отдельно. Повреждённый или отсутствующий объект сначала копируется в staging активного основного корня, сверяется по размеру и SHA-256, получает инертные права и только затем подключается условным обновлением метаданных. Если идентификатор, хеш, размер или ссылка уже изменились, объект пропускается: более новая либо параллельно исправленная версия не откатывается.

Глобальное состояние `server_state` отделено от режимов отдельных дисков. В режиме `read_only` middleware блокирует новые мутации файлов, пользователей, приглашений и конфигурации, а файловый слой повторяет проверку непосредственно перед фиксацией загрузки, закрывая гонку с уже начатой передачей. Активные задания переноса, снимка, зеркала и восстановления переводятся в `cancelled`. Чтение, health, диагностика, отзыв устройства, безопасное завершение Core и проверяемое восстановление остаются доступны оператору.

## Планировщик и проверка резервных копий Alpha 0.5.0a3

`BackupAutomationService` хранит по одной политике на backup-корень: включение, интервал, число сохраняемых копий, основной диск проверки, следующий запуск и последнее задание. Отдельный daemon-поток Core выбирает только просроченные политики и не запускает их в аварийном режиме только чтения. Само задание по-прежнему постоянно хранится в SQLite, поэтому перезапуск не выдаёт незавершённую операцию за успешную.

Проверка восстановления является отдельным постоянным заданием. Она открывает SQLite-копию снимка в режиме только чтения, выполняет `quick_check` и `foreign_key_check`, затем по одному копирует каждый объект из manifest во временную область выбранного основного диска. Размер и SHA-256 сверяются до удаления тестовой копии. Рабочие таблицы `files` и `file_versions` не изменяются.

Ротация применяется только после успешной проверки нового снимка. Удалению подлежат только завершённые и ранее успешно проверенные копии; снимок активного восстановления исключается. Каталог сначала атомарно перемещается из `backups` в карантин `.staging`, затем транзакция фиксирует `pruned_at` и аудит. При ошибке транзакции каталог возвращается на исходное место; после успешной фиксации карантин удаляется.
